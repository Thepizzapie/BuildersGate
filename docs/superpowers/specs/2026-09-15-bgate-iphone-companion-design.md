# Builders Gate — iPhone Companion (design)

Date: 2026-09-15
Status: approved for planning
Transport decision: **Approach A** — phone talks directly to the existing
`bgate_ui` FastAPI over a Tailscale tunnel. No cloud, no separate bridge
service. Full feature parity with the desktop cockpit; multi-project support
from day one.

## 1. Goal

A native SwiftUI iPhone app that monitors and controls a locally-running
Builders Gate project exactly the way the desktop dashboard does, reaching the
machine over the user's Tailscale tailnet. It replaces the cloud path entirely
for phone use.

## 2. Architecture & data flow

```
iPhone app (SwiftUI)  ──HTTP over Tailscale (WireGuard-encrypted)──▶  bgate_ui FastAPI :7788
   BgateAPI client            X-Bgate-Token header                     (existing routes, unchanged)
   Keychain: servers[]        reads = poll, writes = POST              opt-in "remote mode"
```

- Phone reaches the machine at its tailnet IP (`http://100.x.x.x:PORT`), which
  the pairing QR encodes directly. MagicDNS name resolution is deferred to a
  later phase (see §3, §9) — `tailnet.detect()` only ever resolves the bare IP.
- Reads are polled JSON — the same shapes the desktop dashboard already polls.
- Writes are POSTs to the existing mutation routes.
- The app drives the existing dashboard API. No new route logic on the server.

**Boundaries (small, isolated, independently testable):**

- Server change is confined to `bgate_ui/app.py::serve()`, the host gate in
  `bgate_ui/api.py::install_guard`, and one new tailnet-detection helper.
  Zero route changes.
- App networking (`BgateAPI`) is fully isolated from views. Each feature is its
  own view + typed models reading from `BgateAPI`.

## 3. Server: opt-in "remote mode" (the only backend change)

### Current state (verified in code)

- `serve()` binds `uvicorn.run(app, host="127.0.0.1", port=port)`.
- `install_guard` enforces three gates on requests:
  1. **Host gate (anti-DNS-rebinding), runs first, always on:** rejects any
     `Host` whose host part is not in
     `_LOOPBACK_HOSTS = {127.0.0.1, localhost, ::1, 0.0.0.0, testserver}`.
     This runs *before* the safe-method exemption, so it blocks reads too.
  2. **Same-origin gate:** rejects `sec-fetch-site` not in `{same-origin,none}`
     and mismatched `origin`. A native URLSession client sends neither header,
     so it passes cleanly.
  3. **Token gate:** requires `X-Bgate-Token` (or `Authorization: Bearer`)
     matching the per-project token minted at `.bgate/ui-token`.

The host gate is the sole blocker for a phone on the tailnet (its `Host` is the
`100.x.x.x` IP, which is not loopback). Token + same-origin already work for a
native client.

### Change

- **New opt-in:** `bgate serve --remote` (and env `BGATE_REMOTE=1`).
  **Default stays loopback-only** — the current posture is unchanged unless the
  user explicitly opts in.
- When remote mode is on:
  - **Detect the tailnet address:** shell `tailscale ip -4`; fallback to
    scanning local interfaces for an address in `100.64.0.0/10` (CGNAT range
    Tailscale uses). MagicDNS name resolution is **deferred to a later
    phase** — `tailnet.detect()` only ever returns the bare IP today, so no
    MagicDNS name is ever admitted.
  - **Bind to that specific tailnet IP** — not `0.0.0.0`. This exposes the
    dashboard on the tailnet only, never the broader LAN.
  - **Admit exactly the detected tailnet IP** into the host-gate allow-set. It
    remains a *known-host allowlist*, preserving the anti-rebinding property —
    arbitrary `Host` values are still 403.
  - Token remains **required** (unchanged).
  - Print the pairing URL + token and an **ASCII QR** (see §4) to the terminal.
- If tailnet detection fails, remote mode refuses to start with a clear error
  telling the user Tailscale is not up — it never silently falls back to
  `0.0.0.0`.

### Security posture

- Remote is explicit opt-in; default is loopback-only.
- Bind is narrowed to the tailnet interface.
- Token required on every mutation; anti-rebinding host allowlist preserved.
- Plain HTTP over the tailnet is acceptable because WireGuard encrypts the hop;
  this is documented rather than adding redundant TLS. (Revisit if Tailscale
  Serve/HTTPS is later desired.)

## 4. Pairing / QR flow

- `bgate serve --remote` emits a QR encoding JSON:
  `{"url":"http://100.x.x.x:PORT","token":"…","project":"<name>"}`.
- App Settings → **Scan to pair** (AVFoundation, reusing ClaudeGlass's
  `QRScannerView`) writes the server entry to **Keychain** (a secret — not
  UserDefaults).
- Manual entry (URL + token) is the fallback path.
- Because the token is per-project, each QR pairs the phone to one specific
  project's dashboard.

## 5. iOS app (new standalone SwiftUI project)

- New Xcode project generated by XcodeGen `project.yml`, structured like
  ClaudeGlass. Reuses ClaudeGlass's `BridgeAPI`/QR patterns and the OrbitiOS
  design-system component set (Card / Pill / GlassHero), re-skinned to Builders
  Gate branding (`#ff6a3d` orange, BG mark).
- Suggested layout:
  - `App/BuildersGateApp.swift`, `App/BgateTheme.swift`
  - `Net/BgateAPI.swift`, `Net/Models.swift`, `Net/Keychain.swift`,
    `Net/ImageLoader.swift`, `Net/ServerStore.swift`
  - `Views/…` (one file per screen below)
  - `Support/Info.plist` (camera usage string for QR scan)

### `BgateAPI`

- Port of ClaudeGlass `BridgeAPI`: Keychain-backed base+token, `X-Bgate-Token`
  on every request, typed Codable models, a Combine poller (~2–3s cadence,
  backs off when the app is backgrounded), and a token-authed async image
  loader (AsyncImage cannot attach headers, so a custom `URLSession`-based
  loader is required).
- Multi-server: `ServerStore` holds an array of paired servers in Keychain with
  a selected/active server. Switching servers re-points `BgateAPI.base/token`.

### Screens (tab bar)

- **Status** — overview + live seats/agents + activity feed.
- **Queue** — list → item detail; dispatch / stop / steer / create.
- **Review** — the "what you owe an answer on" drain list + artifact approvals
  (approve / reject with note; react).
- **Assets** — library grid → family/revisions → full token-authed preview.
- **Brainstorm** — sessions list → detail + notes (create).
- **Settings** — server switcher, pair (QR / manual), live connection status,
  unpair.

## 7. Error handling

`BgateError` cases and behaviors:

- `notConfigured` → route to pairing screen.
- `unauthorized` (401) → prompt re-pair (token stale/rotated).
- `badHost` (403) → surface "server isn't in --remote mode" with the fix.
- `offline` (tailnet/host unreachable) → retry reads with backoff; show a clear
  connection banner.
- `http(n)` → generic, with the server's error envelope message.

Reads auto-retry with backoff. Mutations never fail silently — every POST
reports success or failure to the user.

## 8. Testing

### Server (pytest)

- Remote mode on: tailnet `Host` + valid token → allowed (read and write).
- Remote mode on: tailnet `Host`, no/wrong token → 401.
- Remote mode on: arbitrary/evil `Host` → still 403 (rebinding protection).
- Remote mode off (default): loopback behavior byte-for-byte unchanged.
- Tailnet-detection helper: unit-tested against faked `tailscale ip` output and
  a faked interface list (including the failure/refuse-to-start path).

### iOS (XCTest)

- `BgateAPI` request building: header attach + base/path join + method.
- Codable decoding against JSON fixtures captured from the real endpoints.
- Error mapping (status code → `BgateError`).
- `ServerStore` multi-server add/select/remove round-trip via Keychain.
- Manual smoke against a locally-run `bgate_ui --remote`.

## 9. Decisions

- **Multi-server from day one** — the app stores multiple paired projects and
  switches between them; each pairs via its own QR/token.
- **No cloud path** for phone use; Tailscale is the transport.
- **No redundant TLS** on top of WireGuard for v1; documented, revisitable.
- **MagicDNS is deferred to a later phase** — `tailnet.detect()` only ever
  resolves the tailnet IP; the phone reaches the machine via that IP, which
  the pairing QR encodes.
- **The pairing QR/token is a long-lived credential shown in plaintext**
  (terminal QR + printed token, per §4). Accepted for Phase 1 because the
  blast radius is tailnet-only (WireGuard-encrypted, opt-in). Short-lived
  pairing codes / token rotation are a Phase 2 concern.
