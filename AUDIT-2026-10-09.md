## 1. Secrets & PII (Critical)

### No secrets found — confirmed explicitly

Scanned **all 591 commits**, not just the working tree, after `git fetch --unshallow`
(the clone arrives shallow at depth 1, which is how a history scan silently becomes a
working-tree scan). Patterns: provider key prefixes (`sk-`, `sk-ant-`, `sk-proj-`,
`ghp_`, `gho_`, `github_pat_`, `AKIA`, `AIza`, `xox[baprs]-`, `glpat-`, `hf_`, `dop_v1_`,
`SG.`), PEM private-key blocks, JWTs, URL-embedded credentials, non-empty `*_API_KEY=`
assignments, and `oauth:` tokens.

**29 secret-shaped lines have ever existed in this repository. Every one is a synthetic
test fixture.** The complete set:

```
AIzaSyAAAA…  AKIAIOSFODNN7EXAMPLE  ghp_AAAA…  glpat-AAAA…  hf_AAAA…
sk-AAAA…  sk-ant-api03-AAAA…  sk-do-not-leak-this-value
sk-live-NOTREAL-abcdefghijklmnop  sk-live-NOTREAL-zyxwvutsrqponm
sk-proj-AAAA…  sk-test-DO-NOT-USE-000000000000abcd
xoxb-NOTAREALTOKEN-AAAA…  BEGIN RSA PRIVATE KEY (3-line stub)
```

They live in `tests/board/test_streamer.py`, `tests/runtime/test_provider_keys.py`,
`tests/ui/test_api_contract.py` and `tests/adapters/test_adapters_adjust.py`, and they
exist to assert that the redaction layer catches them. `AKIAIOSFODNN7EXAMPLE` is AWS's
own published documentation placeholder.

Also checked and clean:

- **No `.env`, `.pem`, `.key`, `.p12`, `.pfx`, `.keystore`, `id_rsa`, `.npmrc` or
  `.pypirc` has ever been committed** in 591 commits. The only tracked env file is
  `.env.example`, and **every value in it is empty**.
- `.gitignore` covers `.env` and `.env.*` with an `!.env.example` exception.
- Emails and absolute user paths in *file contents* are all fixtures or docstring
  examples (`/Users/marta/`, `C:\Users\robin`, `hunter2@github.com`,
  `http://192.168.1.40:8188` in a local-runtime test).
- Token comparison uses `secrets.compare_digest` at **every** one of the four
  verification sites (`api.py:533`, `api.py:579`, `routes/remote.py:48`,
  `routes/voice.py:215`) — no timing-unsafe `==` anywhere on the auth path.
- `src/bgate_core/board/streamer.py` is a purpose-built, one-way redaction layer
  (vendor-shape matching, literal matching against the live process env, URL
  credentials, PEM blocks) with a thorough test class behind it.

### Finding P1 — Real personal data in commit metadata (medium, unchanged since 2026-09-23)

File contents are clean; **commit authorship is not**, and this is now the fourth audit
to report it. Of 591 commits, **584 correctly use a GitHub `noreply` alias and 7 do not**,
across 3 distinct identities:

| Commits | What is exposed |
|---|---|
| 2 | An **external contributor's corporate email address** — a `jgboswell.com` address. Not the maintainer's to publish. |
| 1 | The maintainer's **personal Gmail address**. |
| 4 | A **machine hostname that contains the maintainer's first name** (`*@Adrians-Mac-Studio.local`). |

Local parts are withheld here deliberately — writing them into a tracked Markdown file
would turn git metadata into grep-able, search-indexable page text and make the exact
problem being reported worse.

Metadata can only be changed by rewriting history, which breaks every clone and fork.
The pragmatic fix is forward-looking: set `user.email` to the `noreply` alias on **every**
development machine (the 4-commit cluster is one machine that was never configured), and
ask the external contributor whether they want their corporate address scrubbed. The repo
already shows awareness here — one commit is literally *"Tests use a fictional name, not
the account name"* — so this is a gap in an existing effort, not a blind spot.

### Finding P2 — Confirm the historical credential was rotated (medium, unchanged)

`.github/workflows/security.yml` notes in its own comments that this repo has previously
had a credential committed. **No such credential exists anywhere in the 591 reachable
commits** — it was removed before the current history or rewritten out.

Removal from reachable history is not the same as safety: a public repo retains
unreachable objects, and forks keep independent copies. The action is therefore a
confirmation, not a search — verify that credential was rotated, and verify
**Settings → Code security → Secret scanning + Push protection** is enabled.
`security.yml` recommends exactly this and deliberately declines to add a third-party
scanner in its place, which makes the repository setting the only control covering it.

## 2. Code Quality

The engineering discipline here is well above average, and that is worth stating plainly
before the gaps.

**Verified clean this run:**

- `ruff check .` — **All checks passed.**
- **`pip-audit` reports no known vulnerabilities** against the declared dependency
  floors pinned exactly *and* against the ranges as `pyproject.toml` declares them.
  The Python supply chain is genuinely well managed.
- Exactly **one** TODO/FIXME/HACK marker in 183k lines of Python.
- ~86k lines of tests across 315 files against ~183k lines of Python.
- Four CI workflows (`ci`, `nightly`, `security`, `release-exe`), Dependabot, CodeQL, and
  `pip-audit` run against both the resolved tree and the declared floors.
- **`shell=True` at `src/bgate_ui/agents/claudeusage.py:142` is sound.** It re-runs the
  user's *own* pre-existing `statusLine` command, read back from the bridge file this
  tool wrote from their `~/.claude/settings.json`. A status line is a shell command by
  definition; the input is the user's own configuration, not request data. Reviewed and
  cleared, not a finding.
- The `exec()` calls in `src/bgate_adapters/_blender_*.py` and `blender_live.py` execute
  generated scripts inside the Blender subprocess — the documented design in
  `SECURITY.md`, which states plainly that this tool "executes code and spends money on
  your behalf." Consistent with the stated threat model.
- Path containment is taken seriously: 65 `is_relative_to`/`relative_to` checks across
  the UI and core.

### Finding C1 — Two critical RCE advisories in the scaffold templates shipped to users (critical, unfixed for 3 days)

**This remains the most serious finding in the repository, and it is in the product
surface rather than the repo's own build.** Re-verified live today against both templates:

`bgate init --engine web` scaffolds a user's new game from
`src/templates/web/2d/package.json` or `src/templates/web/3d/package.json`. Both still
pin `vite: ^5.4.0` and `vitest: ^2.1.0`, and **neither ships a lockfile** — so every
scaffolded project resolves fresh. Today that resolves to `vite@5.4.21`, `vitest@2.1.9`,
`tinypool@1.1.1`, `esbuild@0.21.5`, and `npm audit` reports **6 vulnerabilities
(2 critical, 1 high, 3 moderate) in each template**:

| Severity | Package | Advisory |
|---|---|---|
| **CRITICAL** | `tinypool` ≤2.1.1 (via `vitest@2.1.9`) | Prototype pollution gadget in worker options → **RCE** — GHSA-5gmw-xhrv-c9v3 |
| **CRITICAL** | `tinypool` ≤2.1.1 (via `vitest@2.1.9`) | Prototype pollution gadget to RCE in `run()` options — GHSA-85c8-ppgw-ccpr |
| high/moderate | `esbuild` (via `vite` ≤6.4.2) | **Any website can send requests to the dev server and read the response** — GHSA-67mh-4wv8-2f99 |

The esbuild advisory deserves extra weight *in this product's context*: Builders Gate
exists to run a dev server for playtesting and actively instructs the user to start one.
Since the last audit, `12598d7` ("Playtests play web projects: Rebuild runs the vite
build") moved *more* of the product onto that toolchain. "Any website you have open can
read responses from your dev server" is materially worse here than in a generic web app.

The telling detail is unchanged: **the repo's own `frontend/` runs `vite@6.4.3` — exactly
one patch above the vulnerable `≤6.4.2` range.** The toolchain was moved past this
advisory in one place and the templates were left behind. There is no migration cost to
fixing it: a scaffold has no existing code to break, and the project already
demonstrably runs vite 6.

Current safe targets: `vite` ≥6.4.3 (latest 8.3.4), `vitest` ≥5.0.3 (which is what pulls
`tinypool` to ≥2.2.0), and `three` ^0.186 (pinned at `^0.169.0` — no advisory, 17 minor
versions stale).

### Finding C2 — npm is outside every CI control (high, unfixed)

Three independent gaps all land on JavaScript, and together they are why C1 persists:

1. **Dependency updates.** `.github/dependabot.yml` declares `pip` and `github-actions`
   only. **No `npm` ecosystem entry exists**, so neither `frontend/` nor either template
   has an automated update path. Dependabot *alerts* are a separate, repo-wide feature
   and were firing — the gap is that nothing turns an alert into a pull request.
2. **CI gating.** `security.yml` runs `pip-audit` against both the resolved tree and the
   declared floors, which is better than most projects manage. **No `npm audit` step
   exists**, so no build has ever failed on a JS advisory.
3. **Static analysis.** CodeQL is configured `languages: python` (`security.yml:100`).

### Finding N1 — 41 vendored third-party files are outside all dependency management (high, NEW)

Not reported by any previous audit, which counted npm *manifests* and therefore could not
see this. `frontend/public/vendor/` holds **41 tracked files, 29 of them JavaScript**:

| Library | Vendored version | Status |
|---|---|---|
| three.js (+ OrbitControls, TransformControls, GLTFLoader, draco & basis wasm decoders) | `REVISION "169"` | 17 minor versions stale — same drift as the template |
| CodeMirror 5 (13 files: modes, search, dialog, brackets…) | minified, **no version retained** | CodeMirror 5 is end-of-life; CM6 is the successor |
| Tabler icons (woff2) | no version | — |

This is **live, served code**, not a leftover:

- `frontend/public/index.html` (the actual served page — `vite.config` copies `public/`
  verbatim into `src/bgate_ui/static/`) loads CodeMirror.
- `packaging/build_exe.py:131-134` bundles the three.js files into `BuildersGate.exe`.

And it is covered by **nothing**:

- Not declared in `frontend/package.json`, so absent from `package-lock.json` and
  invisible to `npm audit` — including the `npm audit` step recommended in C2.
- No npm Dependabot entry would reach it even once C2 is fixed, because there is no
  manifest to update.
- No `VERSION`, `README` or provenance file in the directory (only upstream `LICENSE`
  files, which is the one thing done right).
- Served locally, so no Subresource Integrity to pin against.

The consequence is not a known advisory today — it is that **there is no mechanism by
which a future advisory in three.js, CodeMirror or the draco/basis wasm decoders would
ever become visible to this project.** Two `.wasm` binaries ship to the browser and into
the signed `.exe` with no recorded upstream version at all.

### Finding N2 — The unanalysed, untested frontend is ~76k lines, not 31k (high, NEW scale)

Previous audits put the CodeQL gap at "31,327 lines of TypeScript." The real number is
**more than twice that**, because the frontend is two parallel UIs:

| Surface | Files | Lines | CodeQL | Unit tests |
|---|---|---|---|---|
| `frontend/public/*.js` — hand-written vanilla JS | 64 | **45,791** | none | none |
| `frontend/src/**` — React + TypeScript shell | 105 | **29,916** | none | none |
| `frontend/public/index.html` — 4 inline `<script>` blocks, 1,143 lines of JS, 24 inline `on*=` handlers | 1 | 1,511 | none | none |
| **Total frontend** | **170** | **~77,200** | **0%** | **0%** |

Against all of that there is **one** test file: `frontend/e2e/critical.spec.ts`,
153 lines, **4 Playwright tests**. And there is no JS unit-test runner configured at
all — `frontend/package.json` declares `build`, `dev`, `e2e` and `typecheck`, with
**no `test` script and no vitest dependency**. The irony is that the templates ship
`vitest` to users while the repo's own frontend has no unit-test runner.

The Python side, by contrast, has ~86k lines of tests across 315 files. A handful of
Python tests (`tests/misc/test_wf_steps.py`, `tests/board/test_wf_model_steps.py`,
`tests/misc/test_nodecanvas.py`) do assert against the classic JS by parsing it as text,
which is inventive but is not behavioural coverage.

The dual-UI split is itself the maintainability finding: 45k lines of vanilla JS and 30k
lines of React implement one product, and `vite.config.ts` carries a long comment
explaining the arrangement — a sign it is understood to be confusing. Consolidation is a
large project and not an audit's call, but the *coverage* gap is cheap to close.

### Finding N3 — A broken `.gitignore` rule is still publishing a file (low, unchanged)

`.gitignore:54` reads:

```
.github\instructions\codacy.instructions.md
```

Backslashes are **escape characters** in gitignore syntax, not path separators. The
pattern matches nothing; `git check-ignore` confirms the file is **not ignored**, and
`.github/instructions/codacy.instructions.md` is tracked and public. It is the only
backslash pattern in the file.

The file is not sensitive, but it is an auto-generated vendor agent-instruction file
scoped `applyTo: '**'` that tells any AI agent reading the repo *"YOU MUST IMMEDIATELY
run the codacy_cli_analyze tool… Failure to follow this rule is considered a critical
error."* That competes directly with `CLAUDE.md` for any contributor using an agent.
Someone intended to exclude it; the rule just never worked.

Fix: `git rm --cached .github/instructions/codacy.instructions.md` and change the line to
forward slashes.

## 3. Suggested Enhancements

Prioritised by security first, then maintainability, then performance.

**1. Bump the scaffold templates off vite 5 / vitest 2 — security, ~15 minutes.**
The only item here that affects *users* rather than contributors, and the only one
carrying a critical rating. In both `src/templates/web/2d/package.json` and
`src/templates/web/3d/package.json`: move `vite` to `^8` (anything ≥6.4.3 clears the
esbuild advisory), `vitest` to `^5` (clears both `tinypool` criticals), and `three` to
`^0.186`. A scaffold has no existing code to break and this repo's own frontend already
runs vite 6, so the usual "major bump = migration project" objection does not apply.
Then **commit a lockfile with each template**, or have `init` run `npm install` and keep
the result — an unlocked scaffold inherits whatever the range resolves to on the day the
user runs it, which is precisely how this drifted. This has now been the top finding for
three days across two audits; it is a 15-minute change.

**2. Put npm under Dependabot and gate CI on `npm audit` — security, ~20 minutes.**
Add `package-ecosystem: "npm"` entries to `.github/dependabot.yml` for `/frontend`,
`/src/templates/web/2d` and `/src/templates/web/3d`, and an
`npm audit --audit-level=high` step to `security.yml` beside the existing `pip-audit`
jobs. Add `javascript-typescript` to the CodeQL `languages` list — that one line takes
~77k lines of code from zero static analysis to the same treatment Python already gets.
**Do this in the same sitting as item 1**, because it is what stops item 1 from
recurring; fixing the versions without fixing the pipeline just resets the clock.

**3. Bring `frontend/public/vendor/` under management — security/maintainability, ~1 hour.**
Pick one of two routes. Either (a) declare `three` and `codemirror` as real
`frontend/package.json` dependencies and import them through the bundler, deleting the
vendored copies — which puts them inside `npm audit`, Dependabot and the lockfile in one
move; or (b) if vendoring must stay (offline-first for the `.exe` is a legitimate
reason), add a `frontend/public/vendor/VERSIONS.md` recording the exact upstream version
and source URL of every file, plus a CI step that diffs those pins against the npm
registry. Route (a) is strongly preferable and would also shrink the repo. Either way,
treat the CodeMirror 5 → 6 question separately — CM5 being end-of-life is a slow problem,
but an unversioned wasm decoder in a signed binary is the part worth closing now.

**4. Give the frontend a unit-test runner and a smoke suite — maintainability, ~half a day for real value.**
Add `vitest` and a `test` script to `frontend/package.json` and wire it into `ci.yml`
next to the existing `typecheck` and `frontend-drift` jobs. Even 20–30 tests over the
highest-traffic modules would be a step change from four e2e tests across 170 files, and
the infrastructure cost is close to zero since vite is already the build tool. Target the
state and data-shaping helpers first — the pure functions in `public/*.js` and the React
hooks — rather than DOM rendering, which is where the cost/benefit is worst and where the
Playwright tests already reach.

**5. Close the commit-metadata gap going forward — privacy, ~10 minutes.**
Set `git config user.email` to the GitHub `noreply` alias on every machine used for this
project; the 4-commit cluster is one unconfigured machine, and 584 of 591 commits already
do this correctly. Add a `core.hooksPath` pre-commit check or a `CONTRIBUTING.md` line so
the next machine inherits it. Separately, ask the external contributor whether they want
their corporate address scrubbed — that decision is theirs, not the project's. Rewriting
history to remove the existing 7 is **not** recommended: it breaks every clone and fork
for a disclosure that is already public.
